# 15_Directory_Enumeration

## Objective

Identify accessible directories, REST endpoints, API routes, profile resources, and administrative paths exposed by the OWASP Juice Shop application. The assessment focused on mapping the application's attack surface, discovering publicly accessible resources, differentiating protected endpoints from public ones, and analyzing server responses to support subsequent security testing activities.

---

## Burp Suite Tools Used

- **Proxy** – Captured HTTP requests generated by the browser.
- **Target Site Map** – Identified application structure and available endpoints.
- **Intruder** – Performed automated endpoint and directory enumeration using a custom payload list.

---

## Target Endpoints

```http
GET /<payload>
GET /api/<payload>/
GET /rest/<payload>
GET /profile/<payload>
```

---

# Testing Methodology

## 1. Root Directory Enumeration

Burp Suite Intruder was configured in **Sniper** attack mode to enumerate resources directly under the application root.

The following request pattern was used:

```http
GET /<payload>
```

A custom payload list containing common application directories and resources was supplied to Intruder.

Example payloads included:

- admin                          - cards
- api                            - card
- rest                           - checkout
- login                          - quantities
- users                          - profile
- user                           - assets
- products                       - images
- product                        - ftp
- basket                         - uploads
- basketitems                    - robots.txt
- addresss                       - swagger
- complaints                     - docs
- feedbacks                      - config
- deliverys                      - appliaction
- productitems                   - administration

### Observation

The application returned different HTTP status codes depending on resource availability.

Observed behavior included:

- **HTTP 200 OK** for publicly accessible resources.
- **HTTP 301 Moved Permanently** for redirected resources.
- **HTTP 500 Internal Server Error** for unsupported or invalid requests.

The response status codes and response lengths were compared to identify potentially valid application resources.

---

## 2. API Endpoint Enumeration

The following endpoint pattern was tested:

```http
GET /api/<payload>/
```

Enumeration targeted RESTful API resources exposed under the application's API namespace.

The same payload list was reused during testing.

### Observation

Testing produced multiple response types including:

- HTTP 200 OK
- HTTP 401 Unauthorized
- HTTP 500 Internal Server Error

Protected API resources correctly required authentication, while publicly available endpoints remained accessible without authentication.

Response length comparison was also used to distinguish valid endpoints from invalid requests.

---

## 3. REST Endpoint Enumeration

REST resources were enumerated using the following request pattern:

```http
GET /rest/<payload>
```

The objective was to identify REST services exposed by the application.

### Observation

Enumeration identified both public and protected REST endpoints.

Observed responses included:

- HTTP 200 OK
- HTTP 401 Unauthorized
- HTTP 500 Internal Server Error

Unauthorized responses indicated that authentication controls were enforced for selected REST resources.

---

## 4. Profile Resource Enumeration

Profile-related resources were enumerated using:

```http
GET /profile/<payload>
```

Testing focused on identifying accessible profile resources and validating whether profile-related functionality required authentication.

### Observation

Most publicly available profile resources returned:

```http
HTTP/1.1 200 OK
```

No unintended directory listing or sensitive information disclosure was observed during testing.

Response analysis assisted in identifying valid application routes.

---

# Response Analysis

During directory enumeration, multiple HTTP response codes were observed.

| Status Code | Observation |
|-------------|-------------|
| **200 OK** | Publicly accessible resource identified |
| **301 Moved Permanently** | Resource redirected successfully |
| **401 Unauthorized** | Authentication required to access resource |
| **500 Internal Server Error** | Invalid or unsupported endpoint |

Differences in response length and server behavior were used to distinguish valid application resources from non-existent or protected endpoints.

# Security Observations

## Public Resource Discovery

Directory enumeration successfully identified several publicly accessible application resources including login functionality, product-related endpoints, static assets, and REST services.

Publicly accessible resources consistently returned **HTTP 200 OK**.

---

## Authentication Enforcement

Several API and REST resources returned **HTTP 401 Unauthorized**, indicating that authentication controls were enforced before access to protected functionality was granted.

This behavior demonstrated that access control mechanisms were implemented for selected application endpoints.

---

## Response Behaviour Analysis

Enumeration revealed noticeable differences in HTTP status codes and response lengths.

These differences allowed valid resources to be distinguished from invalid endpoints and assisted in mapping the application's attack surface for subsequent security testing.

---

## Application Mapping

Directory enumeration provided a comprehensive overview of the application's structure by identifying root directories, API routes, REST services, profile resources, administrative endpoints, and supporting application components.

The discovered endpoints formed the basis for later testing activities including Authorization Testing, Parameter Manipulation, Authentication Testing, and API Security Assessment.

# Conclusion

Directory Enumeration was performed using Burp Suite Intruder to identify publicly accessible resources, API endpoints, REST services, profile-related functionality, and protected application routes.

Testing demonstrated that the application exposed several public resources while correctly enforcing authentication for selected API and REST endpoints through **HTTP 401 Unauthorized** responses.

Response code comparison and response length analysis proved effective for identifying valid resources and differentiating them from invalid or restricted endpoints.

Overall, the assessment successfully mapped the application's attack surface and established a foundation for subsequent security testing phases including Authorization Testing, Parameter Manipulation, Authentication Assessment, and API Security Evaluation.
